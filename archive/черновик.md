## Ошибки

При изменении обработки ошибок выясни выбранную библиотеку и её API по техдокументации проекта и README библиотеки.

- Используй выбранную общую библиотеку для каждой ошибки модуля, которую можно представить её средствами после передачи зависимости. Создавай, оборачивай и объединяй ошибки средствами этой библиотеки.
- Обычный `error("message", 0)` допустим только пока модуль не может пользоваться библиотекой ошибок, например если её зависимость отсутствует или некорректна. В этом случае прекращай выполнение; такие строковые ошибки загрузки не включай в `ERROR`.
- Если модуль может выбрасывать объекты общего типа ошибки, предоставь публичную таблицу `ERROR` в возвращаемой таблице модуля. Храни в ней только стабильные строки первопричин и создавай исходные ошибки только из них, чтобы вызывающий код мог классифицировать сбои.
- Динамические сообщения, пути, идентификаторы, имена операций и тексты исключений добавляй только в контекст оборачивания ошибки.
- Если модуль не может содержательно обработать ошибку, при необходимости добавь контекст своей операции и выброси объект через `error(err, 0)`. Не подавляй ошибку, не возвращай `nil, err`, не продолжай работу после записи в лог и не придумывай запасной сценарий.
- Каждый уровень добавляет свой контекст; цепочка должна читаться от операции верхнего уровня к вложенным причинам. Верхний уровень решает, показывать ли ошибку, логировать её или останавливать процесс.

**Пример:**

```text
push apply button: save settings in storage: C# storage bridge save call: invalid path
```

## Логирование

- Активно используй уровень `trace`: отмечай начало и завершение этапов, выбранные ветви и ключевые параметры. Не дублируй каждую строку кода.
- Записывай ошибку с уровнем `ERROR` там, где принимается решение о её обработке. Низкоуровневый код, который не может содержательно обработать сбой, передаёт его выше с контекстом.

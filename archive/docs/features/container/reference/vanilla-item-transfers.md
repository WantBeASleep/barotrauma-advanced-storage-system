# Ванильный перенос предметов: проверка кода

[К правилам переноса](../README.md#перенос-при-нехватке-места)

Проверено 20 октября 2026 года по открытой ветке master официального репозитория FakeFishGames/Barotrauma. Это чтение исходников, не игровой тест и не подтверждение совпадения с установленной сборкой. Ссылки на master изменяемые.

## Что подтверждено

| Участок | Наблюдение | Источник |
| --- | --- | --- |
| Обработка двойного клика | Выбирается вся группа из слота, половина или один предмет по действиям ввода TakeHalfFromInventorySlot и TakeOneFromInventorySlot. Привязки к Shift/Ctrl отдельно не проверялись. | [Клиентский Inventory.cs](https://github.com/FakeFishGames/Barotrauma/blob/master/Barotrauma/BarotraumaClient/ClientSource/Items/Inventory.cs) |
| Обработка doubleClickedItems и QuickUseItem | Предметы обрабатываются по одному. PutToContainer вызывает TryPutItem; TakeFromContainer пробует активный вложенный инвентарь экипировки, затем инвентарь персонажа. Есть отдельные ограничения количества за действие, например при помещении в слот экипировки. | [Клиентский CharacterInventory.cs](https://github.com/FakeFishGames/Barotrauma/blob/master/Barotrauma/BarotraumaClient/ClientSource/Items/CharacterInventory.cs) |
| Inventory.TryPutItem без указания слота | Если допустимого слота нет, возвращает false до вызова PutItem. Сама неудача не требует сброса предмета. CanBePut проверяет возможность размещения, включая стаки. | [Общий Inventory.cs](https://github.com/FakeFishGames/Barotrauma/blob/master/Barotrauma/BarotraumaShared/SharedSource/Items/Inventory.cs) |
| Получение персонажем | TryPutItemWithAutoEquipCheck и TryPutItem учитывают обычные слоты, экипировку и разрешённые размещения. Поэтому занятые обычные слоты и руки — недостаточная универсальная проверка отсутствия места. | [Общий CharacterInventory.cs](https://github.com/FakeFishGames/Barotrauma/blob/master/Barotrauma/BarotraumaShared/SharedSource/Items/CharacterInventory.cs) |

**Вывод для обычного переноса:** последовательные попытки допускают частичный успех; не принятые получателем предметы остаются в источнике. Это основание выбранного правила мода. Количество, запрошенное действием, и возможность принять его — разные ограничения: отсутствие лимита длины строки не означает выдачу всей строки одним двойным кликом.

## Исключения и границы

В TryPutItemWithAutoEquipCheck есть специальная ветка замены экипировки: если допустимые слоты заняты и AllowDroppingOnSwapWith разрешает замену, уже экипированный предмет может быть сброшен. Поэтому утверждение «любой быстрый перенос в ваниле никогда ничего не выбрасывает» неверно. Это поведение замены экипировки, а не общий способ разместить остаток партии. [Исходник](https://github.com/FakeFishGames/Barotrauma/blob/master/Barotrauma/BarotraumaShared/SharedSource/Items/CharacterInventory.cs).

У деконструктора есть явные вызовы Drop после неудачного помещения в выходной инвентарь: например, при обработке содержимого разбираемого предмета в tryPutInOutputSlots. Таким образом, сброс задаётся отдельной механикой поверх попытки переноса. [Deconstructor.cs](https://github.com/FakeFishGames/Barotrauma/blob/master/Barotrauma/BarotraumaShared/SharedSource/Items/Components/Machines/Deconstructor.cs).

Консольная выдача здесь отдельно не исследована. Поведение всех механизмов генерации предметов этим исследованием не обобщается.

## Что проверить при реализации

- Сопоставить исходники с поддерживаемой версией игры и проверить действия в игре, включая частичную выдачу и заполненные руки.
- Сохранить привычные действия ввода; точное количество для действий над длинной строкой списка определить в UI.
- Отделить обычное получение запаса из меню от специальных действий экипировки. Решение о переносе не отменяет ванильные замены экипировки; их вызов из нового UI требует отдельной проверки.
- Проверить, что неудача переноса не удаляет предмет из источника и не создаёт копию, в том числе при одновременной работе игроков.

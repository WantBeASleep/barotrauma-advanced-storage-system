# Документация и исходники Barotrauma

Получай контекст по самой игре: форматы контента, смысл настроек и реализация механик. Для XML начни с документации моддинга; для вопроса о внутреннем поведении — с исходников. Читай связанные определения и места использования, необходимые для ответа, а не весь справочник.

## Граница с LuaCs

- Этот навык объясняет, что делает оригинальная игра и как описывается её контент.
- Для API платформы, хуков, загрузки скриптов и плагинов, экспорта типов и вызовов из Lua используй [luacs-docs](../luacs-docs/SKILL.md).
- Если вопрос пересекает обе области, сначала установи игровое поведение, затем проверь способ обращения к нему через платформу. Наличие метода в C# игры не подтверждает его доступность из Lua; изменения LuaCs могут отличаться от оригинальной реализации.

## XML и свойства контента

1. Определи вид контента и элемент, которому принадлежит настройка. Различай определение типа предмета (`ItemPrefab`), экземпляр (`Item`), компонент и вложенный элемент XML.
2. Прочитай страницу типа: атрибуты, дочерние элементы, компоненты и ссылки на исходники `Relevant files`, если они есть. Для компонента прочитай также общие свойства базового компонента по ссылке страницы.
3. Для нужной настройки выясни точное XML-имя, тип, значение по умолчанию, допустимые значения и единицы, смысл и условия действия. Проверь зависимость от других параметров, вложенность и наследование/переопределение, когда они участвуют в задаче.
4. Найди подходящий пример в документации или ванильном `Content`. Пример показывает конкретную конфигурацию; он не определяет все допустимые значения и не доказывает обязательность каждого атрибута.
5. Если описание отсутствует, неполно или противоречит наблюдаемому поведению, проследи чтение XML и использование значения в исходниках нужной версии. Ищи имя атрибута, C#-свойство, атрибуты `[Serialize(...)]`, вызовы чтения XML и `SerializableProperty`. Свойство может загружаться вручную; наличие публичного C#-свойства само по себе не делает его XML-атрибутом.

Не переноси одинаково названное свойство между уровнями XML без проверки. Отсутствие настройки на странице не доказывает, что игра её не поддерживает.

**Пример:** чтобы разобраться в XML контейнера, открой `Item`, затем [ItemContainer](https://regalis11.github.io/BaroModDoc/ItemComponents/ItemContainer.html) и `ItemComponent`. Установи, какие атрибуты относятся к предмету, какие — к компоненту, какие элементы он принимает. При вопросе о стаках отдельно проверь `MaxStackSize` предмета и контейнера, затем чтение и применение этих ограничений в коде.

## Как разбирать игровую механику

В репозитории игры основные каталоги исходников расположены так:

| Путь от корня репозитория | Назначение |
| --- | --- |
| `Barotrauma/BarotraumaShared/SharedSource` | Общий код игры |
| `Barotrauma/BarotraumaClient/ClientSource` | Клиентская часть |
| `Barotrauma/BarotraumaServer/ServerSource` | Серверная часть |

Для предметов начни с `Items/Item.cs`, `Items/ItemPrefab.cs`, `Items/Inventory.cs` и `Items/Components` внутри соответствующего каталога. Для эффектов — с `StatusEffects`. Остальные сущности находи по имени в дереве выбранной версии; не угадывай путь файла.

1. Сформулируй конкретный вопрос: что запускает действие, какие данные оно читает, что меняет и при каких условиях. Выбери поисковые слова: класс, метод, XML-ключ, идентификатор контента, текст ошибки или английское название механики.
2. Найди определение и реализацию. В локальной копии используй `rg --files` для поиска файлов и `rg -n` для символов; без неё — дерево и поиск репозитория на GitHub. Не ограничивайся первым совпадением или объявлением метода.
3. Прочитай вызывающий код, существенные проверки, изменения состояния и используемые вспомогательные методы. Для настройки проследи цепочку «чтение XML → сохранение значения → применение»; для действия — «вызов → условия → результат».
4. Проверь базовые классы, перегрузки и другие части `partial`-класса, если они участвуют в поведении. Для сетевой механики проследи клиентскую и серверную части, условия `CLIENT`/`SERVER`, отправку события и его обработку. Код в Shared сам по себе не доказывает одинаковое выполнение на обеих сторонах.
5. Сопоставь реализацию с конфигурацией контента. Разделяй возможности механизма и настройки конкретного ванильного предмета. Заверши поиск, когда установлены условия и результат, нужные для задачи.

**Пример:** чтобы понять, почему предмет не помещается в контейнер, найди проверки приёма в `ItemContainer` и `Inventory`, затем места их вызова и участвующие ограничения XML. Если поведение различается в мультиплеере, проверь также серверную обработку перемещения; одной клиентской проверки интерфейса недостаточно.

## Поиск и доступ к источникам

- Если оглавление не дало ответа, ищи `site:regalis11.github.io/BaroModDoc/ <термин>` или `repo:FakeFishGames/Barotrauma <символ>` в поиске GitHub. Открывай найденную страницу или файл: сниппет не заменяет чтение.
- Переходи по реальным ссылкам индекса и `Relevant files`. Если ссылка устарела, найди файл по имени в текущем дереве, затем выбери нужную версию.
- Если GitHub не показывает текст, используй Raw для найденного файла, доступный API репозитория или локальную копию. Для нескольких файлов достаточно адресного чтения; широкое исследование удобнее вести по локальному checkout вне репозитория мода. Не добавляй копию исходников игры в мод ради получения контекста.
- Если сайт документации недоступен, ищи соответствующий материал в репозитории BaroModDoc; если описания нет — в исходниках игры. При недоступности всех подходящих источников обозначь, что осталось неподтверждённым.

## Версии и результат

Когда ответ зависит от версии, установи целевую версию игры по данным проекта или установленной игры и выбери соответствующий тег/коммит исходников. Проверь соответствие, а не только сходство имени тега. Онлайн-документация и `master` могут описывать другую версию; если сопоставить их не удалось, укажи использованную ревизию и ограничение вывода.

При расхождении документации и кода ориентируйся на реализацию целевой версии и явно назови расхождение. Для поведения под LuaCs отдельно проверь изменения платформы через `luacs-docs`.

В ответе или описании решения кратко укажи вывод и подтверждающие страницы/файлы; для исходников предпочитай ссылки на конкретный коммит и строки. Отделяй описанное в документации, установленное по коду и ещё не проверенные предположения. Не выдавай чтение исходников за проверку в запущенной игре.

Уже прочитанный контекст можно использовать повторно, если вопрос и версия не изменились. Механическая правка, не затрагивающая игровое поведение или формат контента, не требует нового обхода источников.

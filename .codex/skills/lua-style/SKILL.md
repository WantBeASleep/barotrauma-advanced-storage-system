# LuaRocks: стиль Lua

Применяй следующие правила при работе с Lua-кодом. Основа — [LuaRocks Lua Style Guide](https://github.com/luarocks/lua-style-guide) без обоснований и вводных пояснений. Документация адаптирована под LuaCATS; для модулей обязательны файлы определений `.d.lua`.

## Контракты и инварианты

* Перед изменением поведения выясни контракт по документации API, определениям типов, реализации и местам вызова. При противоречиях проследи путь выполнения; если остаётся существенная неоднозначность ожидаемого поведения, уточни её у пользователя.
* Не меняй контракт попутно с другими изменениями. Сохраняй обязательность значений и допустимые типы, если задача не требует их пересмотра.
* Считай отсутствие значения допустимым только тогда, когда это предусмотрено контрактом.
* Не маскируй нарушение контракта значениями по умолчанию, преобразованиями, созданием зависимостей или подавлением ошибок. Применяй такие действия только там, где они предусмотрены контрактом.

## Документация

* Документируй функции через LuaCATS, указывая все параметры и возвращаемые значения, включая необязательные значения и ошибки. При написании и проверке аннотаций и файлов `.d.lua` используй [справочник LuaCATS](references/luacats.md).
* Предпочитай документацию над функцией о её назначении комментариям внутри функции о реализации. Делай реализацию достаточно простой, чтобы пояснения не требовались; сложные функции разбивай на функции с понятными именами. Комментарии должны быть содержательными, не пересказывай очевидные операции.

## Файлы определений модулей `.d.lua`

* Для каждого Lua-модуля обязательно создавай отдельный файл определений с тем же базовым именем: `storage.lua` → `storage.d.lua`. Файл определений храни в папки модуля.
* Размещай определения публичного API модуля в его .d.lua. Аннотации внутренних функций, локальных переменных и уточнения типов оставляй рядом с соответствующим кодом.
* Обновляй `.d.lua` вместе с изменениями публичного API. Определения должны соответствовать реализации.
* Правила написания, подключения и пример см. в [справочнике LuaCATS — модули и определения](references/luacats.md#модули-и-определения).
* Для именованных типов в аннотациях используй устойчивый префикс библиотеки или модуля. Локальные переменные классов называй без этого префикса. **Пример:** класс `Animal` в модуле `zoo` должен иметь аннотацию `zoo.Animal`.

## Имена переменных

* Чем шире область видимости, тем подробнее имя. Однобуквенные имена допустимы для областей меньше 10 строк и для итераторов.
* Используй `i` только как счётчик в числовом `for` или цикле с `ipairs`.
* В циклах с `pairs` предпочитай содержательные имена вместо `k` и `v`; исключение — функции для произвольных таблиц.
* Используй `_` для игнорируемых переменных.
* Имена переменных и функций пиши в `snake_case`.
* Имена классов пиши в `CamelCase`, аббревиатуры — с одной заглавной буквой (`XmlDocument`). Методы называй в `snake_case`.
* Для функций, возвращающих логическое значение, предпочитай префикс `is_`.
* Используй `UPPER_CASE` умеренно и только для констант.
* Не используй имена из заглавных букв, начинающиеся с `_`: они зарезервированы Lua.

## Таблицы

* По возможности заполняй поля таблицы сразу при её создании.
* По возможности используй запись `key = value`; для ключей, которые нельзя записать идентификатором, используй `["key"] = value`. Избегай смешения этих форм в одном объявлении.

## Объявление функций

* Разбивай сложные выражения на понятные подвыражения с содержательными именами.
* Для именованных функций предпочитай `local function name()` присваиванию `local name = function()`.
* Выполняй проверки и возвращай результат как можно раньше.

```lua
local function is_good_name(name, options, args)
   if #name < 3 or #name > 30 then
      return false -- ранний возврат
   end

   -- ...stuff...

   return true
end
```

## Доступ к полям таблиц

* Для известных полей используй точечную запись.
* Используй `[]`, если ключ задаётся переменной или таблица используется как список.

## Функции в таблицах

* Функции модулей и классов объявляй вне конструктора таблицы.
* Функции метатаблиц объявляй внутри конструктора таблицы.

## Объявление переменных

* Всегда объявляй переменные с `local`.

## Область видимости переменных

* Объявляй переменные в минимально необходимой области видимости.

## Условные выражения

* Используй краткие проверки истинности, если не нужно различать `false` и `nil`: оба значения ложны в условиях.
* Избегай API, зависящих от различия между `nil` и `false`.
* Используй `and`/`or` как псевдотернарный оператор, когда это упрощает код. Во вложенных выражениях используй скобки.
* Не применяй `x and y or z` как замену тернарного оператора для возвращения логических значений или значений, которые могут быть `nil`: при `y == false` или `y == nil` выбирается `z`.

## Типы

* В коде, не критичном к производительности, можно проверять типы аргументов через `assert`.
* Используй стандартные функции преобразования типов; не полагайся на неявное приведение.

## Ошибки

* При ожидаемом сбое, например ошибке ввода-вывода, возвращай `nil` и строковое сообщение об ошибке. После них можно вернуть дополнительные значения, например код ошибки.
* При неправильном использовании API или нарушении внутренних инвариантов вызывай `error()` или `assert()`.

## Модули

* Сохраняй границы ответственности модуля. Предметные сущности, правила и константы, непосредственно относящиеся к его назначению, могут быть частью реализации. Значения и решения, принадлежащие использующему модуль коду, передавай через параметры, настройки или явные зависимости. Не добавляй служебному модулю знание конкретной механики или проекта, если оно не требуется для его собственной задачи. Не вводи настройки и абстракции только ради гипотетического переиспользования.
* Размещай каждый модуль в отдельной папке.
* Добавляй в папку каждого модуля `README.md`: кратко объясняй, какую задачу решает модуль, за что отвечает. Можешь привести примеры использования или контракт если модуль является распространненым универсальным пакетом. (Например логер, или пакет ошибок)

* Начинай модуль с объявления локальной таблицы. Её имя должно быть полностью в нижнем регистре и совпадать с именем переменной при подключении.
* Выбирай имена модулей, не конфликтующие с локальными переменными; избегай имён вроде `size`.
* В модуле используй local function для внутренних функций, недоступных снаружи. Если внутренней функции нужен доступ к состоянию объекта, объявляй её методом через : и помечай аннотацией ---@private.
* Публичные функции API модуля, включая `new`, объявляй в таблице модуля через точку. Публичные методы экземпляра объявляй в таблице класса через двоеточие.
* Не создавай глобальных переменных в модуле. В конце всегда возвращай таблицу.
* Если модуль должен вызываться как функция, задай его таблице метаметод `__call`.
* Подключение модуля не должно иметь побочных эффектов, кроме загрузки других модулей и возврата таблицы модуля.
* Основной файл модуля называй `modulename.lua`. 
* Используй основной файл модуля как публичную точку входа. В составных модулях сосредотачивай в нём сборку публичного API; внутренние файлы самостоятельно подключают необходимые им модули.

## Загрузка модулей и зависимости

* Подключай Lua-модули через `require`. Не используй `dofile` или `loadfile` для получения отдельных экземпляров модуля: экземпляры создаёт его конструктор.
* Сохраняй результат `require` в локальную переменную с именем последнего компонента полного имени модуля. Не переименовывай подключаемые модули произвольно.
* Записывай `require` как обычный вызов функции со скобками.
* Разделяй загрузку модуля и создание объектов. Загружаемый модуль возвращает таблицу публичного API; зависимости конкретного экземпляра и его настройки передаются в `module.new(...)`. Повторный `require` одного имени возвращает закешированный результат, общий для потребителей в одном Lua-окружении.
* Библиотеки, которые модуль использует непосредственно и которым не требуется настройка со стороны вызывающего кода, подключай через локальный `require` в использующем их файле, обычно в начале файла. Не требуй передачи таких библиотек через конструктор без конкретной необходимости.
* Готовые объекты зависимостей, выбор и настройка которых принадлежат вызывающему коду, принимай через `new(...)`. Например, адаптер хранилища принимает уже созданное соединение с C#-хранилищем.
* Выбирай параметры конструктора по смыслу: небольшое число понятных обязательных аргументов передавай позиционно; для нескольких настроек и зависимостей используй таблицу с именованными полями. Не вводи общий контейнер зависимостей, если объекту нужны только отдельные значения.
* Не передавай зависимости экземпляра через аргументы загрузки файла, глобальные переменные или настройку общей таблицы модуля. Пути, необходимые для работы с ресурсами, могут быть параметрами объекта; для подключения Lua-модулей используй их имена.
* Избегай циклических зависимостей между модулями. Разрывай их выделением общей функциональности или передачей готовой зависимости при создании объекта.

### Имена модулей в LuaCs

* Используй полное устойчивое имя модуля с namespace. Несовместимые версии общих пакетов подключай под разными именами.
* Учитывай, что LuaCs выбирает первое совпадение среди модов: одинаковое имя не позволяет выбрать конкретную физическую копию. Поставляемые под одним именем реализации должны быть взаимозаменяемыми. См. [загрузку модулей в LuaCs](https://evilfactory.github.io/LuaCsForBarotrauma/lua-docs/manual/getting-started/#including-other-files).

## Конструкторы и состояние объектов

* Если модуль создаёт настраиваемые объекты или объекты с состоянием, предоставляй функцию `module.new(...)`. Модулю с обычными функциями без состояния конструктор не требуется.
* Каждый успешный вызов `new(...)` возвращает новый экземпляр, готовый к использованию по своему контракту.
* Храни зависимости и изменяемое состояние экземпляра в самом экземпляре. Не записывай их в таблицу модуля, таблицу класса или общие локальные переменные файла.
* Создавай принадлежащие экземпляру изменяемые таблицы внутри конструктора, включая вложенные коллекции. Новая внешняя таблица не обеспечивает независимость, если её изменяемые поля ссылаются на общее состояние.
* Общими могут быть методы, константы и данные, которые используются только для чтения. Создание нового экземпляра не должно менять настройки или состояние ранее созданных экземпляров.
* Переданные объекты зависимостей сохраняй по ссылке. Несколько экземпляров могут намеренно использовать одно соединение или другой общий сервис; отдельный экземпляр не означает копирование внешних ресурсов.
* Не изменяй переданную таблицу настроек как собственное рабочее состояние. Если объекту нужны изменяемые коллекции из настроек, создай принадлежащие ему копии нужных данных либо явно закрепи совместное использование в контракте.
* Функцию конструктора объявляй и вызывай через точку: `storage.new(connection)`.

## ООП

* Создавай классы по следующему образцу. **Пример:**

```lua
local storage = {}

local Storage = {}
local Storage_mt = { __index = Storage }

function storage.new(connection)
   assert(connection ~= nil, "connection is required")

   local self = {
      connection = connection,
      pending = {},
   }

   return setmetatable(self, Storage_mt)
end

return storage
```

* Таблица класса и его метатаблица должны быть локальными. Метатаблицу с метаметодами можно объявить на верхнем уровне как локальную переменную `MyClass_mt`.
* Вызывай методы экземпляра через двоеточие: `store:save(...)`.
* Не используй `__gc` для освобождения ресурсов, отличных от памяти. Для файлов и подобных ресурсов предоставляй метод `close`; не закрывай их автоматически через `__gc`.

## Структура файлов

* Имена Lua-файлов пиши полностью в нижнем регистре.
* Разделяй файл, когда из него можно выделить связную часть с понятной ответственностью и это упрощает чтение. Не дроби тесно связанную логику так, чтобы для её понимания приходилось постоянно переключаться между файлами.

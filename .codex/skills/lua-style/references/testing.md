# Тесты на Lua: Busted и Luassert

Busted задаёт структуру тестов и их жизненный цикл; Luassert предоставляет проверки, spies, stubs и matchers. Внутри тестов Busted эти средства доступны как `describe`, `it`, `assert`, `spy`, `stub` и `mock`.

## Где искать информацию

- [Busted: Defining Tests](https://lunarmodules.github.io/busted/#defining-tests) — блоки, подготовка данных, очистка и изоляция.
- [Luassert](https://github.com/lunarmodules/luassert#readme) — проверки, сопоставление аргументов и расширение библиотеки.
- [Busted: Spies, Stubs & Mocks](https://lunarmodules.github.io/busted/#spies-mocks-stubs) — наблюдение за вызовами и подмена функций.

При использовании незнакомого API прочитай соответствующий раздел. Если документация расходится с поведением установленной версии, проверь исходники и тесты нужного тега в репозиториях [Busted](https://github.com/lunarmodules/busted) и [Luassert](https://github.com/lunarmodules/luassert).

## Из чего состоит тест

| Конструкция | Назначение |
| --- | --- |
| `describe("контекст", function() ... end)` | Группа; вложенные группы уточняют условия. |
| `it("ожидаемое поведение", function() ... end)` | Сценарий: подготовка → действие → проверка. |
| `before_each(function() ... end)` | Подготовка перед каждым дочерним тестом. |
| `after_each(function() ... end)` | Очистка после каждого дочернего теста. |
| `setup` / `teardown` | Подготовка и очистка на уровне группы. |
| `finally(function() ... end)` | Очистка после текущего теста, в том числе при его падении. |

Изменяемые данные создавай внутри `it` или заново в `before_each`. Общая подготовка группы подходит для ресурсов, которыми тесты могут пользоваться независимо. Изоляция файлов Busted не заменяет очистку состояния между тестами.

**Пример:** тест модуля `queue` с контрактом `new()`, `push(value)` и `pop()`; пустая очередь возвращает `nil`.

```lua
local queue = require("queue")

describe("Очередь", function()
   local subject

   before_each(function()
      subject = queue.new()
   end)

   it("возвращает значения в порядке добавления", function()
      subject:push("first")
      subject:push("second")

      assert.are.equal("first", subject:pop())
      assert.are.equal("second", subject:pop())
   end)

   it("возвращает nil для пустой очереди", function()
      assert.is_nil(subject:pop())
   end)
end)
```

## Как выбирать проверки

Семантика и примеры — в [Busted: Asserts](https://lunarmodules.github.io/busted/#asserts).

| Проверка | Что проверяет |
| --- | --- |
| `assert.are.equal(expected, actual)` | Равенство через `==`, включая действие `__eq`. |
| `assert.are.same(expected, actual)` | Глубокое сравнение содержимого таблиц. |
| `assert.is_true(value)` / `assert.is_false(value)` | Именно `true` / `false`. |
| `assert.is_truthy(value)` / `assert.is_falsy(value)` | Истинность по правилам Lua; `nil` и `false` ложны. |
| `assert.is_nil(value)` | Отсутствующее значение. |
| `assert.has_error(function() ... end, expected_error)` | Исключение; ожидаемую ошибку можно уточнить вторым аргументом. |

Для сравнения передавай ожидаемое значение первым, фактическое вторым. Выбирай проверку по контракту: `truthy` не подтверждает boolean-тип, а `same` не подтверждает идентичность объекта. Возврат `nil, err` проверяй как два результата; это не исключение для `has_error`.

## Подмены зависимостей

- `spy.on(object, "method")` отслеживает вызовы и выполняет исходную функцию; `stub(object, "method")` заменяет её без исходных побочных эффектов.
- `mock(object)` оборачивает функции таблицы рекурсивно в spies; `mock(object, true)` — в stubs. Предпочитай точечную подмену нужной зависимости.
- Вызовы проверяй через `assert.spy(fn).was.called_with(...)` или `assert.stub(fn).was.called_with(...)`. Для методов с `:` учитывай первый аргумент `self`; для идентичности аргумента используй `match.is_ref(object)` из `require("luassert.match")`. См. [Matchers](https://lunarmodules.github.io/busted/#matchers).
- Восстановление подмены через `replacement:revert()` или `mock.revert(object)` регистрируй в `finally` сразу после её создания либо обеспечивай через `after_each`. Очистка после последнего assertion может не выполниться при падении теста.

## Практики написания

- Проверяй публичный контракт и наблюдаемые результаты. Ожидания выводи из требований, не копируй алгоритм реализации в тест.
- Один `it` описывает один сценарий; связанных проверок может быть несколько. Название должно объяснять ожидаемое поведение и значимые условия.
- Выбирай обычные, граничные и ошибочные случаи по контракту. Для таблицы однотипных случаев давай каждому случаю различимое имя отдельного `it`.
- Сохраняй независимость от порядка тестов, текущего времени и случайных данных. Управляемые часы, генератор и внешние зависимости передавай через предусмотренные API.
- Подменяй внешние зависимости, сохраняя проверяемую логику настоящей. Проверяй вызовы зависимостей, когда сами взаимодействия входят в контракт.
- Выноси повторяющуюся подготовку в небольшие фабрики; входные данные и ожидаемый результат должны оставаться понятными из теста.

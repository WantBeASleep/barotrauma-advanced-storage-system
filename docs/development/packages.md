# Пакеты в namespace

Соглашение определяет размещение, версии и сопровождение переиспользуемых Lua-пакетов. Правила написания кода, `require`, конструкторов и зависимостей описаны в [lua-style](../../.codex/skills/lua-style/SKILL.md) и здесь не повторяются.

## Размещение и имена

- Общие пакеты храни в `Lua/<namespace>/pkg/<package>/v<major>_<minor>_<patch>/`. Namespace проекта — `limanchel`; `pkg` расположен рядом с каталогами модов, а не внутри них.
- Код конкретного мода храни в `Lua/<namespace>/<mod-name>/`. Не выноси его в `pkg` только ради разделения на файлы.
- Имя пакета сохраняй между версиями. Полная версия входит в путь; точки заменяются подчёркиваниями, поскольку в имени `require` точки разделяют каталоги.
- Каждая версия содержит весь пакет: публичную точку входа `<package>.lua`, внутренние модули, определения и README. Собственные внутренние файлы подключай из выбранной версии; другие пакеты — как версионированные зависимости.
- Потребители подключают публичную точку входа. Внутренние файлы не являются публичным API, если пакет явно не объявил иначе.

**Пример:** пакет `errors` версии `1.2.3` хранится в `Lua/limanchel/pkg/errors/v1_2_3/errors.lua` и подключается как `require("limanchel.pkg.errors.v1_2_3.errors")`.

## Версии и контракт

- Используй [SemVer 2.0.0](https://semver.org/lang/ru/): `major.minor.patch`, без ведущих нулей. В README указывай полную версию с точками; она должна совпадать с каталогом.
- `major` повышай при несовместимом изменении публичного контракта; `minor` — при совместимом расширении или объявлении API устаревшим; `patch` — при совместимом исправлении. При повышении `major` обнуляй `minor` и `patch`, при повышении `minor` — `patch`.
- Контракт включает публичные имена, параметры, результаты, ошибки, поведение и обещанные форматы данных. Исправление ошибки реализации не требует major, если восстанавливает заявленный контракт. Изменение самого обещанного поведения оценивай как изменение контракта.
- `0.y.z` допускается для начальной разработки; `1.0.0` закрепляет стабильный публичный API. Нулевая версия не отменяет согласование несовместимых изменений.
- Номер назначай пакету целиком, независимо от версии мода. Несколько изменений до выпуска объединяй в одну версию по самому значительному изменению.
- Выпущенную версию не переписывай: изменения выпускаются под новым номером. Совместимые версии также получают отдельные каталоги; выбор другой версии не должен зависеть от порядка загрузки модов.

## Обязательное согласование несовместимых изменений

**Если изменение требует повышения major, до изменения контракта и версии обязательно получи разрешение пользователя.** Общее поручение доработать пакет не заменяет такого разрешения. Если конкретный вариант уже явно согласован в текущем обсуждении, повторное разрешение не требуется.

Перед запросом выясни текущий контракт и известные места использования. Кратко перечисли, что перестанет работать, и предложи выбор:

1. Перевести текущую разработку пакета на новую major-версию и обновить согласованных потребителей.
2. Создать отдельную копию пакета с новой major-версией для параллельного использования; прежнюю версию и её потребителей сохранить.
3. Изменить текущую разработку без повышения версии, **только если пользователь явно подтвердил отсутствие клиентов и разрешил это исключение**. Отсутствие вызовов в доступном репозитории не доказывает отсутствие клиентов: это знает разработчик. Исключение позволяет менять ещё не выпущенный контракт; сохранённые выпущенные релизы не переписываются.

До ответа не выполняй несовместимую правку, не создавай новую major-копию и не мигрируй потребителей. Это правило также действует для несовместимых изменений в `0.y.z`. Старую версию не удаляй без явного разрешения: её клиенты могут находиться в других модах.

## Зависимости и поставка

- Фиксируй точные версии прямых зависимостей в именах импорта и README пакета. Не вводи пути `latest`, алиасы только на major или автоматический выбор «подходящей» версии: `require` LuaCs не разрешает диапазоны SemVer.
- Для каждой версии указывай в README источник исходников, зависимости и существенные требования к среде, включая сторону выполнения и C#-мост, если они нужны. Там же кратко записывай изменения версии и необходимые действия при переходе.
- У пакета должен быть один источник исходников. Копии в модах поставляй из него целиком; одинаковые namespace, имя и полная версия должны означать одинаковое содержимое. Не исправляй поставляемую копию независимо под прежним номером.
- Поставляй необходимые версии пакетов вместе с модом либо объявляй обязательный мод-зависимость, который их предоставляет. Не рассчитывай на случайно установленный другой мод.
- Обновление зависимости требует проверки потребителя. Если меняется выпущенный пакет, выпусти его новую версию; уровень повышения определяется его собственным контрактом, а не автоматически major-версией зависимости.
- Для новой версии проверяй заявленный контракт и известные сценарии потребителей. Обновляй импорты только у тех потребителей, которые переводятся на неё; остальные продолжают использовать прежнюю версию.

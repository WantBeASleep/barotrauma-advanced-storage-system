# Построение UI Barotrauma по схемам

Статус: проект для согласования. Выбранный подход согласован; описанные ниже детали API и схемы предложены автором документа и требуют утверждения вместе с ним.

## Назначение и границы

Самостоятельный Lua-пакет создаёт штатный UI Barotrauma по заранее описанному дереву. Автор интерфейса переносит состав, вложенность, геометрию и оформление в конфигурацию; вызывающий Lua-код получает исходные игровые объекты и связывает их с данными и поведением.

Согласовано с пользователем:

- Пакет универсален, не зависит от хранилищ и других фич мода.
- Размещение использует штатные возможности Barotrauma, включая `RectTransform` и игровые контейнеры. Собственный механизм вёрстки не разрабатывается.
- Схема представляет дерево компонентов; доступ по идентификатору возвращает сам GUI-объект.
- Формат — JSON. Вызывающий код читает файл и передаёт строку пакету; пакет сам разбирает документ, проверяет схемы и выбирает нужную заготовку по имени.
- Первые примеры — абстрактные меню с основными элементами и простыми обработчиками, например кнопкой изменения надписи.
- В пакете есть `manual_test` со схемами, Lua-кодом запуска и подключения логики. Их можно проверять человеку и агенту; unit-тесты нужны отдельно.
- Архивный `ui_runtime` не задаёт архитектуру, формат или совместимость нового пакета.

Пакет не реализует игровой сценарий меню, синхронизацию, реактивное состояние, язык выражений, автоматическую привязку событий, CSS, виртуальный DOM и редактор схем. Управление данными и поведением остаётся в Lua.

Ошибочным результатом считаются скрытые ограничения GUI небольшим списком виджетов, необходимость вручную исправлять родителя стандартного контейнера, молчаливое игнорирование полей и появление обёрток, закрывающих исходный API.

## Подходы

| Подход | Преимущества | Цена |
| --- | --- | --- |
| Описание вызовов конструкторов и присваиваний API | Максимально близко к ручному созданию | Схема повторяет детали вызовов, перегрузок и порядка создания |
| Дерево компонентов с описаниями типов | Единая структура схемы; особенности конструкторов и контейнеров спрятаны в пакете | Для каждого типа требуется описание создания и жизненного цикла |

Пользователь выбрал второй подход. Исходные объекты возвращаются напрямую; описания типов находятся внутри пакета и могут расширяться потребителем. Собственные сокращения для расчёта вёрстки обсуждались отдельно и не выбраны.

## Среда и размещение

Предложение автора: имя `ui_schema`, начальная версия `0.1.0`, каталог `Lua/limanchel/pkg/ui_schema/v0_1_0/`, вход `ui_schema.lua`. Для модулей нужны `.d.lua`; документация и пояснения пишутся на русском.

Среда — клиент Barotrauma, Lua 5.2 через LuaCs/MoonSharp. Создание UI на выделенном сервере возвращает понятную ошибку до создания объектов. Загрузка чистых модулей проверки схем не требует клиента. Пакет не добавляет собственный C#-мост и не меняет регистрацию игровых типов при простом `require`.

Установленная `Barotrauma.dll` сообщает версию `1.13.5.0` и ревизию `c6e8829143c98162ed376aee33eb9799602365ac`. На этой ревизии исходников LuaCs проверены таблица экспорта GUI, внутренний контейнер `GUIListBox` и добавление/удаление консольных команд. Это проверка исходников, а не запуска в игре. Перед реализацией конкретных описаний типов нужно подтвердить их конструкторы и экспорт в установленной среде; README фиксирует проверенную версию.

Ожидаемые ошибки представлены пакетом `limanchel.pkg.goerrors.v0_1_0.goerrors`. JSON-декодер — внутренняя зависимость пакета; его выбор и особенности не перекладываются на потребителя. При использовании декодера LuaCs его контракт и доступность проверяются при реализации. Другие зависимости не планируются. Встроенного логгера нет: ошибки возвращаются потребителю, тестовый запуск сам выбирает вывод.

## Вход и формат схемы

Пакет принимает строку JSON. Вызывающий код только читает файл; разбор JSON, проверка документа, представление схем и выбор именованной заготовки принадлежат пакету. Публичных функций чтения файлов в пакете нет. YAML не поддерживается.

Предлагаемая структура JSON-документа: `schema_version = 1` и объект `components` с именованными схемами. Каждая схема описывает один корневой компонент с его вложениями. Один файл может содержать несколько схем; их также можно распределить по разным файлам.

После разбора пакет возвращает непрозрачный для потребителя документ. Вызывающий код передаёт его обратно пакету вместе с именем компонента, не извлекая внутренние Lua-таблицы. Документ можно многократно использовать для независимых построений; он не накапливает игровые объекты.

**Пример:** `menu` описывает окно, поиск и пустой контейнер списка; `item_row` отдельно описывает строку с иконкой, названием и кнопками. Lua строит меню, затем создаёт и удаляет нужное число экземпляров `item_row` внутри контейнера. Строки заранее не перечисляются в схеме меню; отдельный язык шаблонов не нужен.

Поля узла:

| Поле | Назначение |
| --- | --- |
| `type` | Обязательное имя зарегистрированного типа, например `Frame` или `ListBox` |
| `id` | Необязательная непустая строка; уникальна во всём одном построении |
| `rect` | Описание штатного `RectTransform`, если он создаётся для этого типа |
| `constructor` | Именованные параметры выбранного конструкторного варианта типа |
| `props` | Начальные присваивания публичных свойств и полей созданного объекта |
| `children` | Упорядоченный плотный массив дочерних узлов |
| `attach_to` | Необязательное имя области родителя; допустимые области объявляет тип родителя |

Пропущенные `constructor`, `props` и `children` означают пустые таблицы. Пропущенный `id` означает отсутствие записи в индексе. `rect` обязателен только для типов, которым он нужен; самоуправляемые окна и вспомогательные GUI-объекты могут создаваться иначе. Неизвестные структурные поля, версия схемы и типы отклоняются, а не пропускаются.

`constructor` использует имена параметров нативного конструктора. Описание типа определяет варианты перегрузок, обязательные параметры, значения по умолчанию и допустимые сочетания. В неоднозначном случае поле `constructor.variant` выбирает документированный вариант; это зарезервированное поле описания типа, а не аргумент игры. Пропуск необязательного параметра сохраняет нативное значение по умолчанию; явное отсутствие значения описывается отдельно.

`rect` содержит `size` и необязательные `anchor`, `pivot`, `scale_basis`, `props`. `size` — типизированный `Point` для абсолютного размера либо `Vector2` для относительного. Остальные значения соответствуют нативным перечислениям и свойствам `RectTransform`; пакет не приписывает им собственные единицы, масштабирование или правила размещения. Родитель передаётся построителем и не переопределяется через `rect.props`.

`props` сохраняет точные имена игровых членов, включая регистр. Допускаются пути к существующим внутренним объектам, например `TextBlock.TextColor`; промежуточные объекты не создаются. Присваивание неизвестному или недоступному для записи члену — ошибка с путём в схеме. Это не перечень только заранее выбранных удобных свойств: допустимость окончательно определяет API объекта в целевой среде.

Порядок ключей объекта JSON не имеет значения. Чтобы поддержать зависимые нативные присваивания без языка операций, `props` и `rect.props` принимают также упорядоченный массив записей `{ member, value }`. Объект применяется в порядке имён; массив — в указанном порядке, в том числе с повторным присваиванием. Пакет различает объекты и массивы при разборе JSON; пустые объект и массив означают отсутствие присваиваний. Изменение самого родителя и переназначение созданного `RectTransform` через `props` запрещены: структура принадлежит дереву.

## Значения и ссылки

Схема состоит из данных, без исполняемого Lua и имён глобальных функций. Обычные строки, конечные числа и логические значения передаются без неявного изменения типа. Плотные массивы и словари разрешены там, где этого требует параметр. Необязательное поле и явно переданное нативное `nil` различаются.

Предложенные специальные записи:

| Запись | Результат |
| --- | --- |
| `{ "$type": "Point", "value": [400, 240] }` | Значение нативного типа через зарегистрированный преобразователь |
| `{ "$enum": "Anchor", "value": "Center" }` | Именованное значение зарегистрированного перечисления |
| `{ "$ref": "window", "member": "RectTransform" }` | Созданный объект по `id` или его существующий член; `member` необязателен |
| `{ "$resource": "item_sprite" }` | Готовое значение из контекста вызывающего кода |
| `{ "$nil": true }` | Явный нативный `nil` |

Специальная запись содержит ровно один маркер и только его допустимые поля. JSON `null` в этом формате отклоняется; явное отсутствие значения описывается через `$nil`. Невалидные числа отклоняются. Различение JSON-значений и обработка особенностей декодера остаются внутри пакета.

Начальный набор преобразователей включает `Point`, `Vector2`, `Vector3`, `Vector4`, `Rectangle`, `Color` и `Identifier`; конструкторы, диапазоны и форма аргументов документируются. Перечисления регистрируются по фактическому клиентскому API. Ресурсы позволяют передать любой другой допустимый нативный тип без попытки описать его внутреннее устройство в JSON. Дополнительные преобразователи можно зарегистрировать явно.

Контекст ресурсов задаётся на одно построение и не сохраняется глобально. Например, вызывающий код предоставляет готовые спрайты, шрифты, локализованные строки или делегаты, необходимые конструктору `CustomComponent`. Код делегата остаётся в Lua, а схема только ссылается на готовую зависимость. Чтение файлов, поиск глобальных объектов и вычисление выражений по содержимому схемы не выполняются.

Ссылки в `props` разрешаются после создания всех узлов, поэтому допустимы ссылки вперёд. Ссылка в аргументе конструктора разрешена только на уже созданный в обходе дерева объект; ссылка на себя, потомка или более поздний узел в этой позиции отклоняется заранее с пояснением. Обход — родитель перед детьми, дети в порядке массива. Ресурс из контекста позволяет передать внешний объект, который должен существовать раньше.

## Универсальность и описания типов

У каждого экземпляра построителя собственный реестр. Описание типа отвечает за проверку параметров конструктора, создание исходного объекта, разрешение областей дочерних элементов и освобождение созданного объекта. Создание и очистка специальных типов должны учитывать их нативные побочные эффекты.

Для обычного компонента область детей — его `RectTransform`; для `ListBox` по умолчанию используется `Content.RectTransform`. У составного компонента можно объявить дополнительные именованные области. `attach_to` выбирает такую область у родителя. Неизвестная область или дети у типа, не принимающего их, — ошибка. Пакет не удаляет и не заменяет внутренние элементы, созданные конструктором игры.

Перед реализацией составляется инвентаризация доступных строительных типов GUI по экспорту и конструкторам целевой версии. Встроенная поддержка охватывает штатные компоненты, а не только виджеты демонстрационного меню: контейнеры, текст и ввод, изображения, выбор, списки, прокрутку, индикаторы, окна, перетаскивание, отсечение и пользовательский компонент. Отдельно проверяются специальные объекты из `GUI`, включая контекстные меню, графики и средства воспроизведения: не все они являются обычными `GUIComponent` и не всем нужен внешний `RectTransform`.

Результат инвентаризации входит в README: тип, варианты создания, области детей, особые требования и статус проверки в игре. Нельзя объявлять поддержанным тип только потому, что его имя есть в экспорте. Недоступность конкретного API установленной версии явно обозначается; её нельзя молча заменять другим виджетом. Служебные фасады, перечисления и абстрактные классы не становятся узлами только из-за наличия в таблице `GUI`.

Механизм регистрации позволяет описать любой дополнительно доступный нативный UI-тип или фабрику без изменения обхода дерева. Фабрика получает проверенные параметры и родителя и возвращает исходный объект, а не обёртку. Для объекта вне обычной иерархии она явно задаёт области детей и очистку. Отсутствие встроенного описания не требует форка ядра. Точные Lua-сигнатуры описаний и инвентаризация перегрузок оставлены разработчику; перечисленные обязанности и возможность расширения обязательны.

В `props` нет фиксированного списка только «статических» свойств: например, `Visible`, `Enabled` и начальный текст можно задавать в схеме. Обработчики обычного поведения назначаются вызывающим кодом после построения. Универсальность не означает описание алгоритма произвольной отрисовки данными: схема создаёт `CustomComponent`, а функцию отрисовки предоставляет Lua.

## Публичный API и жизненный цикл

Предложенный API:

- `ui_schema.new()` создаёт независимый построитель со встроенными описаниями типов и значений.
- `builder:register_type(name, descriptor)` добавляет тип; конфликт имён — ошибка использования, существующее описание не заменяется молча.
- `builder:register_value_type(name, converter)` и `builder:register_enum(name, values)` явно расширяют преобразования значений. Конвертер не получает родительский UI и не должен создавать GUI-компоненты.
- `builder:parse(json_text)` разбирает строку JSON, проверяет структуру документа и возвращает непрозрачный `document, nil` либо `nil, err`. GUI при этом не создаётся. Ресурсы и игровой родитель для разбора не нужны.
- `builder:build(document, component_name, parent, context)` создаёт выбранную по имени схему и возвращает `view, nil` либо `nil, err`. Неизвестное имя компонента — ожидаемая ошибка. `parent` — нативный `RectTransform` или `nil` для самостоятельно размещаемого корня; описание типа проверяет допустимость. Необязательный `context` содержит `resources`; его отсутствие означает пустой набор ресурсов. Сырые Lua-таблицы схем публичный API не принимает.
- `view.root` — исходный объект корневого узла; `view.by_id` — индекс исходных объектов узлов этого построения, доступный только для чтения по контракту.
- `view:get(id)` возвращает тот же объект, что `view.by_id[id]`; отсутствие идентификатора — ошибка использования API. Для необязательного поиска используется `view.by_id[id]`.
- `view:dispose()` освобождает созданное дерево; повторный вызов допустим.

Сам `view` — служебный результат построения, не прокси над GUI. Его нельзя использовать вместо исходного компонента в API игры. `get` и построение не копируют игровые объекты. После `dispose` индекс очищен, `root` отсутствует, `get` сообщает об освобождённом результате. Ранее полученные ссылки больше не пригодны для использования.

Несколько экземпляров одной схемы независимы, одинаковые `id` в них допустимы. Для повторяющейся строки вызывающий код повторно вызывает `build` с тем же документом, именем схемы строки и родителем, хранит возвращённые `view` и удаляет их при необходимости. Повторно читать и разбирать JSON не нужно. Каждый экземпляр имеет собственный индекс; глобальных идентификаторов и автоматического поиска по точечным путям дерева нет.

Исходные объекты можно менять через нативный API. Если потребитель вручную удаляет или переносит узел, индекс не отслеживает это: он хранит ссылки, а не живую модель игры. Для управляемого удаления всего экземпляра рекомендуется `dispose`. Перенос за пределы созданного корня не передаёт владение автоматически: созданный узел по-прежнему будет освобождён своим `view`.

Срок жизни переданных ресурсов остаётся у вызывающего кода: пакет не вызывает `Dispose` у заимствованного спрайта или шрифта. Корневое поддерево принадлежит `view`; добавленные потребителем внутрь него элементы удаляются вместе с ним по нативным правилам. Освобождение не затрагивает другие дочерние элементы внешнего родителя.

Пакет не устанавливает постоянные хуки рисования или обновления при загрузке и построении. Включение дерева в нужный игровой цикл и момент построения принадлежат вызывающему коду. Тестовый запуск предоставляет готовый пример этой интеграции.

**Пример:** схема создаёт `Button` с `id = "change_message"` и `TextBlock` с `id = "message"`; Lua получает их через `get`, назначает кнопке нативный обработчик и меняет нативное поле текста. Конкретные сигнатуры обработчиков сверяются с установленным API при реализации примера.

## Построение и ошибки

Пакет разделяет разбор документа и построение выбранной схемы:

1. В `parse` разобрать JSON, проверить версию и структуру документа и схем, форму значений и коллекций. При синтаксической ошибке вернуть понятную причину и позицию в JSON, если её сообщает декодер.
2. В `build` найти выбранную схему, проверить типы, уникальность `id` внутри неё, ссылки, ресурсы, области детей и известные требования конструкторов без создания GUI. Используются текущие регистрации построителя.
3. Создать узлы в порядке дерева. Для каждого подготовить `RectTransform` и его настройки до создания детей, затем вызвать соответствующую фабрику. Регистрировать созданные объекты сразу, чтобы учесть частичный сбой.
4. После создания объектов применить `props` узлов в порядке обхода дерева; внутри каждого узла — в определённом выше порядке присваиваний. Разрешить ссылки на созданные объекты. Если нативному типу нужна финализация размещения, её выполняет описание типа.
5. Вернуть готовый `view` только после успешной настройки всех узлов.

Проверка до создания не обещает доказать допустимость произвольного публичного свойства через рефлексию. Неизвестный нативный член, отказ конструктора, преобразования или setter могут обнаружиться при исполнении. Тогда созданные объекты освобождаются в обратном порядке, результат не возвращается. Сохраняются исходная причина и, если была, ошибка очистки; не выдаётся ложная гарантия отката побочных эффектов чужой некорректной фабрики.

Встроенные описания должны корректно удалять также нативные регистрации самостоятельных окон и прочие собственные побочные эффекты. Для сторонних описаний это часть контракта. Ресурсы вызывающего кода и существующие соседи внешнего родителя при откате сохраняются.

Ошибки JSON, схемы, отсутствие ресурса и отказы игрового API возвращаются как `nil, err`. Неверный тип аргумента публичного Lua API или некорректная регистрация — строковая ошибка использования. Диагностика схемы содержит этап, путь вида `components.menu.children[2].props.TextColor`, `type`, имеющийся `id` и причину. На уровне ядра ничего не печатается и не подменяется значениями по умолчанию сверх заявленных.

## Проверки

### Unit-тесты

Тесты Busted под Lua 5.2 располагаются рядом с модулями. Разбор проверяется на строках JSON через реальный декодер пакета; создание GUI — с подменами фабрик и нативных значений. Тесты проверяют контракт данных и владения, а не имитируют отрисовку:

- Разбор корректного и ошибочного JSON, различение объектов, массивов и `null`, выбор именованной схемы и ошибку неизвестного имени.
- Корректное дерево, порядок детей, выбор внутренних областей и идентичность объектов в индексе.
- Независимость построителей и повторных построений из одного разобранного документа, локальность `id`.
- Типизированные значения, явный `nil`, ресурсы, ссылки вперёд в свойствах и отклонение недопустимых конструкторных ссылок.
- Полезную диагностику неизвестных полей, типов, ресурсов, дубликатов `id` и неверной формы коллекций.
- Порядок присваиваний и передачу нативных значений без неявных преобразований.
- Откат при сбое посреди создания или настройки, освобождение перенесённого узла, повторное освобождение и сохранность чужих ресурсов и соседей.
- Отсутствие GUI-побочных эффектов при загрузке и клиентскую границу построения.

Изменённый Lua проходит форматирование и линт по правилам проекта. Реальное соответствие конструкторов и размещение проверяются в клиенте, а не объявляются подтверждёнными подменами.

### `manual_test`

Папка внутри версии пакета содержит README на русском, схемы JSON, небольшой Lua-запуск и обработчики. Запуск читает файлы и передаёт их содержимое пакету строками, затем выбирает схемы по имени через его API. Собственного разбора JSON и извлечения схем в тестовом Lua-коде нет. Папка не загружается автоматически вместе с библиотекой. Запуск явно подключается разработчиком либо агентом; он создаёт собственные команды и временные хуки, которые снимает при остановке/перезагрузке.

Набор сценариев:

1. Геометрия и вложенность: абсолютный и относительный размер, привязки, смещения, штатные группы и вложенные панели.
2. Основные элементы: надпись, кнопка изменения надписи, текстовый и числовой ввод, флажок, ползунок, выпадающий список и индикатор с простыми зависимостями между ними.
3. Составные элементы: прокручиваемый список, добавление и удаление экземпляров строки из отдельной схемы, доступ к объектам каждой строки, дополнительные области составного компонента.
4. Ресурсы и расширение: изображение из предоставленного спрайта, оформление внутренних объектов, `CustomComponent` с Lua-делегатом, зарегистрированный дополнительный тип.
5. Жизненный цикл и ошибки: закрытие/повторное открытие, несколько экземпляров, намеренно неверная схема с диагностикой и отсутствие частично оставшегося окна после отказа.

Сценарии показывают основные функции; дополнительно для каждого встроенного описания типа нужна проверка создания и очистки в подходящей среде. Для специальных объектов с внешними зависимостями фиксируются необходимые ресурсы. В README различаются проверенный сценарий и ещё не выполненная проверка.

Предложенные команды запуска: `ui_schema_test open <case>`, `ui_schema_test step <action>`, `ui_schema_test report`, `ui_schema_test close`, `ui_schema_test stop`. Имена действий и ожидаемые изменения фиксированы для каждого случая. `step` вызывает тестовое действие/обработчик через тестовый Lua-код и проверяет связанное состояние; это не доказательство прохождения настоящего ввода мышью.

После открытия или действия запуск дожидается минимум двух завершённых кадров обновления/отрисовки. Команда отчёта сообщает `ready` только после этого и после выполнения проверок; ожидание ограничено таймаутом и не блокирует игровой поток. Точный доступный хук и этап кадра проверяются при реализации. Отчёт содержит идентификатор запуска, сценарий, действие, ожидаемые и фактические значения, версии среды, размер окна, масштаб UI и геометрию проверяемых компонентов.

Для агента основной способ визуальной проверки — управление клиентом через доступный инструмент работы с компьютером: выполнить тестовую команду, дождаться готовности, скрыть консоль и получить снимок окна. Игровая функция сохранения скриншота для этого не обязательна. Отчёт можно получить из консоли; по возможности запуск также сохраняет его в разрешённый LuaCs каталог игры. Возможность записи и путь проверяются по установленной среде; сетевой сервис или постоянно открытый порт не нужен.

Каждый визуальный снимок сопоставляется с идентификатором запуска и шагом отчёта. Агент оценивает обрезку, наложения, читаемость, прокрутку и ожидаемое изменение. Отдельный проход настоящими кликами и вводом проверяет фокус, попадание курсора и взаимодействие, которые не проверяет команда `step`. Человек может пройти те же действия вручную. Основные сценарии проверяются при обычном и уменьшенном размере окна; конкретные размеры выбираются по возможностям клиентского окружения и записываются в отчёт.

Если клиент недоступен, выполненные unit-тесты не выдаются за проверку GUI. Автономный визуальный прогон требует запущенной игры с LuaCs и инструмента получения снимков/ввода; это требование среды тестирования, а не зависимость библиотеки.

## Критерии готовности

- Вызывающий код передаёт строку JSON; пакет разбирает документ, проверяет и выбирает схемы. Чтение файлов остаётся снаружи.
- Схемы создают штатные GUI-объекты с правильными родителями, порядком и настройками; нативное размещение не дублируется в Lua-коде примеров.
- Вызывающий код получает исходные объекты по `id` и напрямую назначает им простую логику.
- Доступны повторные независимые построения, в том числе строк из отдельной схемы, и явная очистка без накопления окон, команд и хуков.
- Ошибочная схема не оставляет частичный UI; диагностика указывает место и причину.
- Универсальность подтверждается инвентаризацией нативных типов и работающей регистрацией расширения; демонстрационный список элементов не ограничивает архитектуру.
- Unit-тесты, форматирование и линт проходят; результаты выполненных проверок в клиенте подтверждены отчётами и просмотренными снимками. Невыполненные проверки явно перечислены.
- В README описаны формат, публичный API, владение, расширение типов и воспроизведение `manual_test`.

## Решения автора для проверки при согласовании

Пользователь отдельно не выбирал: имя `ui_schema` и версию `0.1.0`; точные поля схемы и специальные записи; конкретные сигнатуры `parse` и `build`; область уникальности `id` на одно построение; явный `view:dispose`; реестр ресурсов; два представления присваиваний; ограничение ссылок в конструкторах; способ управления тестами через консоль и внешний снимок окна. Все эти решения предложены этим документом, а не приписаны пользователю. JSON и разбор внутри пакета при внешнем чтении файлов согласованы отдельно.

Разработчику оставлены выбор и интеграция JSON-декодера, разбиение внутренних модулей, точные сигнатуры описаний типов, таблицы перегрузок и перечислений, конкретные хуки тестового запуска, путь разрешённого отчёта и размеры проверочного окна. Если проверка целевой среды требует собственного C#-моста, ограничения универсальности или изменения формата/владения, это изменение дизайна нужно обсудить до реализации.

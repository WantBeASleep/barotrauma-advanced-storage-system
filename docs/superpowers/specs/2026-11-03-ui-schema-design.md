# UI Barotrauma из JSON: идеи и соглашения

Статус: проект для согласования. Отмеченные как согласованные решения приняты в обсуждении. Названия функций и точная запись JSON пока предложены автором.

Этот документ объясняет, что должен делать пакет и как им пользоваться. Знание устройства GUI Barotrauma не требуется. Игровые термины и примеры JSON разобраны в [пояснениях](2026-11-03-ui-schema-guide.md).

## Задача пакета

Сейчас при ручном создании интерфейса Lua-код должен создать окно, разместить внутри надписи, кнопки и списки, настроить размеры и оформление. Пакет позволит описывать эту часть работы в JSON. Lua останется отвечать за поведение: что показывать, как реагировать на действия игрока и когда добавлять или удалять элементы.

Результат работы — обычные объекты интерфейса Barotrauma. Кнопке можно назначить игровой обработчик нажатия, надписи — изменить текст. Пакет не заставляет делать это через собственные замены игровых методов.

Пакет универсален: меню хранилища — лишь один из возможных потребителей. От архивного `ui_runtime` совместимость не требуется.

## Что уже согласовано

- Формат описания — JSON.
- Вызывающий Lua-код читает файл и передаёт пакету строку. Разбор JSON и знание устройства схем находятся внутри пакета.
- Каждая схема описывает отдельный компонент со всеми его вложениями. Это может быть целое меню или одна строка списка.
- Размеры и размещение используют штатные возможности игры. Собственный механизм вёрстки не создаётся.
- Созданные игровые объекты доступны по идентификаторам, указанным в схеме.
- Нужны unit-тесты и папка `manual_test` с абстрактными меню, простой логикой и возможностью проверки человеком или агентом.

## Кто за что отвечает

| Работа | Ответственный |
| --- | --- |
| Прочитать файл с диска | Вызывающий Lua-код |
| Разобрать строку JSON, найти схему по имени и проверить её | Пакет |
| Создать игровые объекты, их вложенность, размеры и начальное оформление | Пакет |
| Обеспечить показ меню и обработку ввода на нужном игровом экране | Вызывающий Lua-код; готовый пример подключения даёт `manual_test` |
| Заполнить данные, назначить действия кнопок, обновлять содержимое | Вызывающий Lua-код |
| Решить, когда открыть, обновить или закрыть меню | Вызывающий Lua-код |

Пакет не занимается правилами мода, сетевой синхронизацией или вычислением данных для отображения. Также не разрабатываются редактор схем и собственный язык программирования внутри JSON.

Созданные объекты должны участвовать в работе игрового экрана: игра должна рисовать их и передавать им ввод игрока. Такое подключение зависит от места использования меню и остаётся в вызывающем Lua-коде. [Почему это нужно и как будет показано в примерах](2026-11-03-ui-schema-guide.md#как-меню-попадает-на-экран).

## Как из схем собирается интерфейс

Один JSON-документ может содержать несколько именованных схем. Схемы также можно хранить в разных файлах: распределение по файлам не меняет их смысл.

**Пример:** в документе есть две схемы:

- `menu`: окно, поле поиска и пустой список.
- `item_row`: строка с иконкой, названием и кнопкой.

Работающий интерфейс собирается так:

1. Lua читает файл и передаёт строку пакету для разбора.
2. Пакет возвращает подготовленный документ. Lua хранит его, не разбираясь во внутренних таблицах.
3. Lua просит построить `menu` и получает созданное меню.
4. Когда нужны строки, Lua просит построить `item_row` внутри списка нужное число раз.
5. Каждая строка получает свои данные и обработчики. По мере изменения списка Lua добавляет или удаляет строки.

Схема меню не перечисляет будущие строки. Схема строки — многократно используемая заготовка; каждый вызов создания даёт новый независимый экземпляр. Повторно читать и разбирать JSON ради каждой строки не нужно.

Слово «дерево» означает только вложенность: окно содержит список, строка содержит надпись и кнопку. Оно не требует описать весь будущий интерфейс одним большим документом. [Пример JSON с несколькими схемами](2026-11-03-ui-schema-guide.md#несколько-схем-в-одном-документе).

## Что можно описать в схеме

| Часть описания | Что она означает |
| --- | --- |
| Тип | Что создать: панель, надпись, кнопку, список или другой игровой элемент |
| Идентификатор | Имя, по которому Lua сможет получить созданный объект |
| Размер и положение | Где элемент находится внутри содержащего его элемента и сколько места занимает |
| Параметры создания | Значения, которые игра требует уже в момент создания объекта |
| Начальные свойства | Текст, цвет, видимость и другие доступные настройки игрового объекта |
| Вложенные элементы | Что создать внутри этого элемента и в каком порядке |

Поля `type`, `id`, `rect`, `constructor`, `props` и `children` — предложенные обозначения этих частей. Они объяснены вместе с примером в [справке о записи компонента](2026-11-03-ui-schema-guide.md#как-записывается-компонент).

В JSON можно задавать начальное состояние, например текст надписи или скрытую панель. Последующие изменения и действия игрока описываются в Lua. Схема не содержит выполняемый код.

Некоторые значения невозможно записать обычной строкой или числом: например, уже полученное из игры изображение. Для них предлагаются специальные записи. Их назначение — передать игровому объекту нужный параметр. [Наглядные примеры размеров, вариантов, ресурсов и ссылок](2026-11-03-ui-schema-guide.md#как-передавать-параметры-которых-нет-в-json).

## Как работает размещение

Содержащий элемент называется родителем. Например, для кнопки в окне родитель — это окно, а для строки списка — область содержимого списка. Размер и положение обычно задаются относительно родителя.

Barotrauma умеет задавать размеры численно или относительно родителя, привязывать элементы к его краям и центру, располагать их группой и прокручивать список. Пакет создаёт и настраивает эти игровые механизмы. [Объяснение размеров, привязок и контейнеров](2026-11-03-ui-schema-guide.md#размер-положение-и-контейнеры).

У некоторых элементов есть внутренние части, которые игра создаёт сама. Пакет должен знать, куда помещать описанных детей: например, строки должны попадать в прокручиваемое содержимое списка. Автор схемы не обязан вручную исправлять это после построения. Если компонент предлагает несколько областей для вложения, нужную область можно выбрать по имени; предложение для этого поля — `attach_to`.

## Доступ к объектам и подключение логики

Идентификаторы нужны для связи JSON и Lua. Схема даёт кнопке имя `change_message`, а надписи — `message`. Lua получает оба игровых объекта и назначает кнопке действие: изменить текст надписи. [Пример связывания](2026-11-03-ui-schema-guide.md#как-lua-добавляет-поведение).

Поиск действует внутри одного созданного экземпляра. Поэтому в каждой строке списка может быть собственная кнопка с одинаковым `id`: при работе с конкретной строкой Lua получит именно её кнопку.

Пакет возвращает служебный результат построения с доступом к объектам и возможностью удалить экземпляр целиком. Этот результат не заменяет игровые объекты и не ограничивает работу с их обычными свойствами и методами.

## Универсальность и расширение

Поддержка не ограничивается кнопкой, надписью и списком из первого примера. Нужно охватить доступные средства построения UI игры: ввод, изображения, выбор, прокрутку, индикаторы, окна и другие игровые компоненты. Для необычных объектов проверяются их собственные условия создания и удаления.

Пакет хранит знания о том, как создать каждый тип, куда поместить его детей и как удалить результат. Если понадобится ещё один доступный игровой тип, такое описание можно добавить через API пакета без изменения основного алгоритма. [Зачем нужны описания типов](2026-11-03-ui-schema-guide.md#зачем-пакету-описания-типов).

Произвольную отрисовку тоже можно подключить: схема создаёт игровой компонент для неё, а Lua предоставляет функцию рисования. Алгоритм рисования не переводится в JSON.

В README будет список поддержанных типов и реально выполненных проверок. Наличие имени класса в документации само по себе не подтверждает, что он работает через пакет в установленной версии игры.

## Удаление и ошибки

Созданный экземпляр должен удаляться целиком: например, одна строка вместе с её иконкой, надписью и кнопкой. Повторное удаление безопасно. Другие строки и соседние окна остаются на месте. После удаления ранее полученные объекты этого экземпляра использовать нельзя.

Переданные извне объекты, например общий спрайт, принадлежат вызывающему коду: пакет не освобождает их при удалении окна. Подробные правила для ручного переноса элементов и удаления — в [справке о времени жизни](2026-11-03-ui-schema-guide.md#время-жизни-и-ручные-изменения).

Ошибки должны быть понятными: что не получилось, в какой схеме и у какого элемента. Неизвестные поля и неподдержанные настройки не игнорируются. Если создание прервалось посередине, пакет убирает уже созданную часть и возвращает ошибку вместо недостроенного меню. Чужие ресурсы и соседние элементы при этом сохраняются.

## Как проверяем работу

Unit-тесты проверяют разбор JSON, ошибки схем, независимость экземпляров, поиск объектов и правильность очистки. Они не доказывают, что меню хорошо выглядит в игре.

Для проверки в игре внутри пакета создаётся `manual_test`: JSON-схемы, небольшой Lua-запуск и инструкция. Он читает файлы и передаёт строки пакету; собственного разбора схем в примерах нет. Автоматически при загрузке библиотеки эти меню не открываются.

| Сценарий | Что проверяем |
| --- | --- |
| Окно с вложенными панелями | Размеры, положение и порядок элементов |
| Основные элементы управления | Кнопка меняет надпись, ввод и переключатели меняют простое состояние |
| Прокручиваемый список | Создание и удаление отдельных строк, работа с каждой строкой |
| Изображение и дополнительный тип | Передачу готового ресурса и расширение поддержки компонентов |
| Закрытие, повторное открытие и неверная схема | Чистую уборку объектов и понятные ошибки |

Тестовый запуск должен позволять выбрать сценарий и выполнить проверочное действие через консольную команду. После обновления экрана он сообщает, что готов к проверке, и выдаёт отчёт: какое действие выполнено и какие значения получены.

Агент открывает сценарий, выполняет действие, скрывает консоль и получает снимок окна через инструмент управления компьютером. Он сопоставляет снимок с отчётом и проверяет читаемость, наложения, обрезку и прокрутку. Человек может пройти тот же сценарий вручную. Отдельно нужны настоящие клики и ввод: вызов обработчика командой не проверяет, что по кнопке можно попасть мышью. [Подробности тестового запуска](2026-11-03-ui-schema-guide.md#подробности-проверок).

## Что предлагается, но ещё не утверждено

Имя пакета `ui_schema`, версия `0.1.0` и размещение `Lua/limanchel/pkg/ui_schema/v0_1_0/` предложены автором. Предлагаемые имена операций: `parse` для подготовки JSON-документа, `build` для создания выбранной схемы, `get` для получения объекта и `dispose` для удаления экземпляра.

Точная запись полей JSON, обозначения специальных значений, сигнатуры функций и подробные правила обработки описаны в [предложении по формату и API](2026-11-03-ui-schema-guide.md#предложение-по-формату-и-api). Это детализация текущего проекта, а не уже реализованная библиотека. JSON и разделение ответственности за чтение и разбор согласованы отдельно.

Выбор JSON-декодера, разбиение внутренних модулей и конкретные игровые события для тестового запуска оставлены разработчику. Если выяснится, что нужен собственный C#-код или приходится ограничить заявленные возможности, это требует отдельного обсуждения.

## Когда пакет можно считать готовым

- JSON превращается в игровые объекты с нужными вложениями и оформлением; Lua не повторяет их вёрстку вручную.
- Созданные объекты доступны по `id`, и простая логика работает через обычный игровой API.
- Одну схему можно использовать многократно, независимо создавать и удалять строки.
- Ошибки не оставляют частично созданный UI; закрытие не накапливает окна и тестовые обработчики.
- Работает добавление описания дополнительного типа; опубликован список проверенных игровых типов.
- Проходят unit-тесты и обязательные проверки Lua-кода. Примеры проверены в игре, снимки просмотрены, невыполненные проверки явно указаны.
- README объясняет использование пакета и запуск `manual_test`. Требования к среде и исходники для проверки API приведены в [справке](2026-11-03-ui-schema-guide.md#среда-и-проверенные-источники).

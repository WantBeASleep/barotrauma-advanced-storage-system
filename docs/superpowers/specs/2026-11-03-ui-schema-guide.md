# Пояснения к UI Barotrauma и схемам JSON

[К основной спецификации](2026-11-03-ui-schema-design.md).

Здесь объясняются игровые понятия и предлагаемая запись схем. Можно читать только раздел, на который ведёт ссылка из спеки. Пакет ещё не реализован: JSON и Lua ниже иллюстрируют предложенный API, а не готовый к запуску инструмент.

## Из чего состоит интерфейс

Компонент — отдельный элемент интерфейса. Это может быть кнопка, надпись или целая панель с другими элементами внутри. Объект — конкретный созданный экземпляр компонента: три кнопки одного типа будут тремя разными объектами.

| Имя в игровых API и схемах | Простое значение |
| --- | --- |
| `Frame` | Панель: может оформлять фон и содержать другие элементы |
| `TextBlock` | Надпись |
| `Button` | Кнопка |
| `TextBox` / `NumberInput` | Поле текстового / числового ввода |
| `TickBox` | Флажок |
| `Image` | Картинка |
| `LayoutGroup` | Группа, размещающая элементы последовательно по горизонтали или вертикали |
| `ListBox` | Список с областью содержимого и прокруткой |
| `DropDown` | Выпадающий список выбора |
| `ScrollBar` / `ProgressBar` | Полоса прокрутки или ползунок / индикатор заполнения |
| `CustomComponent` | Элемент, отрисовку или обновление которого задаёт функция Lua |

Конструктор — операция создания объекта. Одни параметры передаются при создании, другие можно менять уже у готового объекта. Например, кнопка создаётся с текстом, а её цвет затем можно изменить. Отсюда разделение схемы на `constructor` и `props`: пакет не может одинаково создать все игровые классы одним вызовом.

Обработчик — функция, которую игра вызывает при событии, например при нажатии кнопки. Слово «делегат» в документации C# в этом контексте обозначает такой объект функции с определёнными аргументами.

## Размер, положение и контейнеры

### Зачем нужен `RectTransform`

У большинства компонентов есть объект `RectTransform`. Он отвечает за прямоугольную область элемента: размер, положение и связь с родителем. Сама кнопка отвечает за нажатия и оформление, а её `RectTransform` — за место на экране.

В схемах для него предложено короткое поле `rect`. Создавать `RectTransform` вручную для каждого элемента не потребуется: это делает пакет.

### Абсолютный и относительный размер

**Пример:** нужно задать размер окна численно — 400 на 240. В игре для этого используется `Point`, то есть пара целых чисел:

```json
"size": { "$type": "Point", "value": [400, 240] }
```

Это абсолютный размер по правилам игры. Фактический размер на экране также зависит от штатного масштабирования интерфейса; пакет не вводит дополнительный масштаб.

**Пример:** кнопка должна занимать половину ширины и четверть высоты родителя. Для относительного размера игра использует `Vector2`, пару чисел с дробной частью:

```json
"size": { "$type": "Vector2", "value": [0.5, 0.25] }
```

При обычном расчёте относительно родителя 400 × 240 это даёт область 200 × 60 до учёта остальных игровых ограничений.

Дополнительная настройка `scale_basis` выбирает, от какой стороны родителя считать относительные размеры. `Normal` считает ширину от ширины, высоту от высоты; `BothWidth` считает обе доли от ширины родителя, `BothHeight` — от высоты; `Smallest` и `Largest` — от меньшей или большей стороны родителя. Это особые возможности игры; для первого меню их задавать не требуется.

### Привязка и смещение

`Anchor` выбирает точку на родителе, к которой привязывается элемент: центр, угол или середину края. `Pivot` выбирает точку самого элемента, которая будет совмещена с этой привязкой.

**Пример:** чтобы центр окна совпал с центром родителя, выбираем `Center` для обоих:

```json
"anchor": { "$enum": "Anchor", "value": "Center" },
"pivot": { "$enum": "Pivot", "value": "Center" }
```

Смещение сдвигает элемент от выбранной позиции. Например, `AbsoluteOffset` задаётся через `Point`; минимальный и максимальный размеры — через `MinSize` и `MaxSize`. Эти игровые настройки указываются в `rect.props`. Пакет передаёт их игре и не рассчитывает собственную систему координат.

### Когда контейнер сам размещает детей

У `LayoutGroup` можно выбрать вертикальное или горизонтальное расположение и расстояние между элементами. Если строки помещены в такую группу, вручную вычислять вертикальную координату каждой строки не нужно: это уже делает игра.

У `ListBox` игра сама создаёт внутреннюю панель `Content` и полосу прокрутки. Дочерние строки должны попасть в `Content`, иначе они не станут обычным содержимым списка. Пакет знает это правило и выбирает правильного родителя при построении вложенных узлов.

Когда Lua позднее добавляет отдельно описанную строку, он передаёт место вставки. Для списка это `list.Content.RectTransform`. Это уже работа с полученным игровым объектом; повторять размеры и состав строки в Lua не требуется.

## Несколько схем в одном документе

**Пример:** сокращённый документ ниже показывает только группировку схем; размеры и остальные параметры компонентов здесь опущены:

```json
{
  "schema_version": 1,
  "components": {
    "menu": {
      "type": "Frame",
      "children": [
        { "type": "TextBox", "id": "search" },
        { "type": "ListBox", "id": "rows" }
      ]
    },
    "item_row": {
      "type": "Frame",
      "children": [
        { "type": "TextBlock", "id": "name" },
        { "type": "Button", "id": "take" }
      ]
    }
  }
}
```

`menu` и `item_row` — имена заготовок. `search`, `rows`, `name` и `take` — имена объектов внутри созданного экземпляра. Это два разных назначения имён.

`schema_version` — версия правил записи JSON. Она помогает сообщить об ошибке, если документ использует формат, который пакет не понимает. Она не обязана совпадать с версией самого Lua-пакета.

## Как записывается компонент

**Пример:** это полная предложенная схема небольшого меню с надписью и кнопкой. Расположение вычисляет игра: оба элемента привязаны к центру, надпись сдвинута вверх, кнопка — вниз.

```json
{
  "schema_version": 1,
  "components": {
    "greeting": {
      "type": "Frame",
      "id": "window",
      "rect": {
        "size": { "$type": "Point", "value": [400, 240] },
        "anchor": { "$enum": "Anchor", "value": "Center" },
        "pivot": { "$enum": "Pivot", "value": "Center" }
      },
      "children": [
        {
          "type": "TextBlock",
          "id": "message",
          "rect": {
            "size": { "$type": "Point", "value": [320, 40] },
            "anchor": { "$enum": "Anchor", "value": "Center" },
            "pivot": { "$enum": "Pivot", "value": "Center" },
            "props": {
              "AbsoluteOffset": { "$type": "Point", "value": [0, -35] }
            }
          },
          "constructor": { "text": "Привет" }
        },
        {
          "type": "Button",
          "id": "change_message",
          "rect": {
            "size": { "$type": "Point", "value": [320, 40] },
            "anchor": { "$enum": "Anchor", "value": "Center" },
            "pivot": { "$enum": "Pivot", "value": "Center" },
            "props": {
              "AbsoluteOffset": { "$type": "Point", "value": [0, 35] }
            }
          },
          "constructor": { "text": "Изменить надпись" },
          "props": { "Enabled": true }
        }
      ]
    }
  }
}
```

Смысл полей:

| Поле | Зачем оно нужно |
| --- | --- |
| `type` | Выбрать, какой игровой объект создать |
| `id` | Позже получить конкретный объект из Lua; если доступ не нужен, поле можно пропустить |
| `rect` | Настроить размер и положение; обязателен для типов, которым при создании нужна такая область |
| `constructor` | Передать параметры в момент создания, в примере — начальный текст |
| `props` | Установить настройки уже созданного объекта, в примере — доступность кнопки |
| `children` | Создать вложенные элементы в указанном порядке |
| `attach_to` | При необходимости выбрать именованную область родителя для вложения |

Имена внутри `props` соответствуют игровому API, поэтому `Enabled` пишется с заглавной буквы. Пакет не придумывает второе имя для каждого игрового свойства. Описания поддержанных компонентов в будущем README должны помогать находить нужные настройки.

## Как передавать параметры, которых нет в JSON

JSON умеет хранить строки, числа, логические значения, объекты, массивы и `null`. Он не умеет хранить игровые объекты. Специальные записи ниже — предлагаемая инструкция пакету, какое значение подготовить вместо такой записи.

### `$type`: создать значение игрового типа

Уже показанный `{ "$type": "Point", "value": [400, 240] }` означает: создать `Point(400, 240)`, а не передать игре обычный массив.

Предложенная начальная поддержка:

| Имя | Что представляет |
| --- | --- |
| `Point` | Два целых числа, например абсолютный размер или смещение |
| `Vector2`, `Vector3`, `Vector4` | Набор из двух, трёх или четырёх чисел для соответствующего игрового параметра |
| `Rectangle` | Прямоугольник: положение и размер |
| `Color` | Цвет |
| `Identifier` | Игровой идентификатор, создаваемый из строки |

Формы аргументов и допустимые диапазоны нужно закрепить при реализации преобразователей. Другие готовые игровые значения можно передать через ресурсы.

### `$enum`: выбрать именованный вариант

**Пример:** запись `{ "$enum": "Anchor", "value": "Center" }` выбирает `Anchor.Center`, то есть привязку к центру. Это не произвольная строка «Center», а один из вариантов, которые принимает конкретная настройка игры. Такую группу вариантов в документации называют перечислением.

### `$resource`: взять готовый объект из Lua

**Пример:** Lua уже получил спрайт — игровой объект изображения. Он передаёт его под условным именем `item_sprite`:

```lua
local context = {
   resources = {
      item_sprite = sprite,
   },
}
```

В параметре картинки схема указывает:

```json
"constructor": {
  "sprite": { "$resource": "item_sprite" }
}
```

Пакет подставляет тот же объект `sprite`. Он не читает файл картинки и не пытается восстановить спрайт из JSON. Аналогично можно передать шрифт, игровой текст с поддержкой локализации или функцию, которую требует создаваемый компонент.

### `$ref`: взять объект, созданный по этой схеме

**Пример:** окно имеет `id = "window"`. Если параметру другого компонента нужно это окно, значение записывается как `{ "$ref": "window" }`. Если нужна его область размещения — `{ "$ref": "window", "member": "RectTransform" }`.

`$resource` берёт объект из вызывающего Lua, а `$ref` — среди объектов текущего построения. Ссылки не ищут окна другого экземпляра меню.

### `$nil`: явно передать отсутствие значения

Иногда игра различает «параметр не задан — использовать значение по умолчанию» и «явно передать `nil`». Для второго случая предложено `{ "$nil": true }`. Обычный JSON `null` по этому предложению отклоняется, чтобы не было двух обозначений одного случая.

## Как Lua добавляет поведение

**Пример:** после чтения JSON в переменную `json_text` Lua подготавливает документ и создаёт схему `greeting`. Переменная `parent` здесь — уже существующее место в игровом UI, куда нужно добавить меню:

```lua
local ui_schema = require("limanchel.pkg.ui_schema.v0_1_0.ui_schema")
local builder = ui_schema.new()
local document = assert(builder:parse(json_text))
local view = assert(builder:build(document, "greeting", parent))

local message = view:get("message")
local button = view:get("change_message")

button.OnClicked = function()
   message.Text = "Кнопка нажата"
   return true
end
```

`message` и `button` — исходные игровые объекты. `OnClicked` — игровое поле для функции нажатия; `Text` — свойство текста надписи. Здесь обработчик не использует переданные игрой аргументы и возвращает признак успешного действия.

Этот пример показывает только построение и связывание. Для показа окна также нужно подключение к игровому экрану, описанное ниже.

## Как меню попадает на экран

Игра работает кадрами: обновляет состояние элементов, обрабатывает ввод и рисует результат. Созданный Lua-кодом объект должен попасть в эту последовательность, иначе его наличие в памяти само по себе не обеспечит показ и нажатия.

Способ подключения зависит от места использования. При вставке в существующую игровую панель нужную работу может уже обеспечивать её родитель. Для самостоятельного меню могут потребоваться временные обработчики игровых событий — функции, вызываемые игрой при обновлении или рисовании. Конкретное подключение проверяется в клиенте и остаётся в Lua-коде, который открывает меню.

`manual_test` должен содержать законченный пример: создать меню из JSON, обеспечить его показ и ввод, затем убрать окно и добавленные обработчики. Читателю не придётся восстанавливать эти шаги по справочнику игры. Сама загрузка библиотеки не устанавливает постоянные обработчики для всех будущих меню.

## Зачем пакету описания типов

У окна, списка и картинки разные способы создания. Список дополнительно создаёт внутреннее содержимое; самостоятельное окно может регистрироваться у игры отдельно. Пакету нужно знать эти различия, чтобы единая JSON-схема работала правильно.

Описание типа — Lua-код поддержки одного вида объекта. Оно сообщает пакету, какие параметры нужны, как создать объект, где разместить детей и как всё удалить. В старой технической формулировке функция создания называлась фабрикой: это просто функция, возвращающая новый игровой объект.

Если появился ещё один доступный UI-тип, потребитель добавляет его описание. Основной алгоритм разбора и обхода вложенных компонентов менять не нужно. Описание обязано возвращать сам игровой объект и корректно убирать собственные побочные эффекты при ошибке.

## Время жизни и ручные изменения

Предложенный результат построения называется `view`. Он хранит корневой объект и ссылки на объекты с `id`; это не новый игровой компонент.

`view:dispose()` удаляет созданный экземпляр. Если внутри него Lua добавил другие элементы вручную, они тоже удаляются вместе с содержащим их деревом по правилам игры. Другие дети внешнего родителя не затрагиваются. После очистки `view.root` отсутствует, индекс пуст, повторный `dispose` безопасен.

Если Lua самостоятельно удалил объект, индекс не узнаёт об этом автоматически. Если Lua перенёс созданный объект в другое место, первоначальный `view` всё ещё отвечает за его удаление. Поэтому независимые строки удобно создавать отдельными вызовами `build`: у каждой свой результат и понятный момент удаления.

Общие ресурсы остаются у вызывающего кода. Например, закрытие одного окна не должно освобождать спрайт, которым пользуется второе.

## Предложение по формату и API

Это дополнительные правила проекта для реализации. Они не нужны для знакомства с идеей пакета, но уточняют поведение примеров и пока требуют утверждения вместе со спецификацией.

### Функции

| Вызов или поле | Назначение и результат |
| --- | --- |
| `ui_schema.new()` | Независимый построитель со встроенной поддержкой типов |
| `builder:parse(json_text)` | Разобрать строку и проверить структуру; вернуть `document, nil` или `nil, err`, без создания GUI |
| `builder:build(document, component_name, parent, context)` | Создать выбранную заготовку; вернуть `view, nil` или `nil, err` |
| `view.root` | Исходный объект корневого компонента |
| `view.by_id[id]` | Исходный объект по имени или `nil`, если имени нет; индекс не меняется потребителем |
| `view:get(id)` | Тот же объект; отсутствие имени или обращение после очистки — ошибка использования |
| `view:dispose()` | Удалить созданный экземпляр |
| `builder:register_type(name, descriptor)` | Добавить описание ещё одного типа |
| `builder:register_value_type(name, converter)` | Добавить способ получить игровое значение из записи `$type` |
| `builder:register_enum(name, values)` | Добавить именованные варианты для `$enum` |

`parent` — игровой `RectTransform`. Для самостоятельно размещаемого корня допускается `nil`, если тип умеет так создаваться. Необязательный `context` содержит `resources`; пропуск означает пустой набор ресурсов. При `build` действуют текущие регистрации построителя. Сырые Lua-таблицы схем публично не принимаются.

Регистрации принадлежат своему построителю, конфликт имён вызывает ошибку. Преобразователь значения не должен создавать компоненты интерфейса. Точные сигнатуры Lua-функций внутри описаний типов оставлены разработчику.

### Запись и порядок обработки

- Корень документа содержит `schema_version = 1` и `components`. `id` — необязательная непустая строка, уникальная во всём одном построении. `type` обязателен. Пропуск `constructor`, `props` и `children` означает отсутствие соответствующих настроек или детей.
- `rect` содержит `size`, необязательные `anchor`, `pivot`, `scale_basis` и `props`. Он нужен тем типам, которые требуют область размещения при создании. Самостоятельные окна и вспомогательные игровые объекты могут работать иначе.
- `constructor` использует имена параметров игры. Для выбора неоднозначного варианта создания зарезервировано `constructor.variant`; пропущенный необязательный параметр сохраняет игровое значение по умолчанию.
- Имена в `props` соответствуют доступным свойствам и полям игры. Путь `TextBlock.TextColor` означает изменить цвет уже существующей внутренней надписи; промежуточные объекты не создаются. Менять через `props` родителя или подменять созданный `RectTransform` нельзя: вложенность задаёт схема.
- Объект `props` применяется в порядке имён. Если порядок важен, можно передать массив записей `member` и `value`; тогда сохраняется порядок массива, включая повторные присваивания. Пустые объект и массив означают отсутствие присваиваний.
- Специальная запись содержит ровно один маркер `$type`, `$enum`, `$ref`, `$resource` или `$nil` и только его допустимые поля. Числа должны быть конечными. Пакет сам различает объекты, массивы и `null` при разборе.
- Обычные строки, числа и логические значения передаются без неявного изменения типа. Объекты и массивы допустимы там, где их принимает параметр; необходимые игровые преобразования описываются явно.
- Вложенные компоненты создаются после родителя, в порядке `children`. До создания детей настраивается их родительская область размещения. Обычный компонент принимает детей в свой `RectTransform`, список — в `Content.RectTransform`; дополнительные области объявляет описание типа, выбирает `attach_to`.
- Свойства `props` компонентов применяются после создания всех узлов, в порядке обхода. Поэтому `$ref` в них может указывать на более поздний узел. В параметре создания ссылка допустима только на уже созданный узел: на себя, потомка или более позднего соседа сослаться здесь нельзя. Внешний готовый объект передаётся через `$resource`.
- Ресурсы передаются на одно построение, не сохраняются глобально и не освобождаются пакетом. Схема не ищет глобальные функции, не читает файлы и не вычисляет выражения.

**Пример:** упорядоченное присваивание двух свойств вместо объекта `props` записывается так:

```json
"props": [
  { "member": "Enabled", "value": false },
  { "member": "Visible", "value": true }
]
```

### Ошибки и очистка

`parse` проверяет синтаксис JSON и форму документа. `build` до создания GUI проверяет выбранную схему, имена типов, `id`, ссылки, ресурсы, области детей и известные требования создания. Синтаксическая ошибка содержит позицию в JSON, если её даёт декодер; ошибка схемы — путь вроде `components.menu.children[2].props.TextColor`, тип и имеющийся `id`.

Не каждое ограничение игрового свойства можно проверить заранее. При отказе во время создания или настройки пакет удаляет созданные объекты в обратном порядке и возвращает ошибку. Если очистка тоже не удалась, её причина сохраняется вместе с первоначальной. Встроенные описания учитывают также регистрации самостоятельных окон у игры. У сторонних описаний корректная очистка — обязанность автора; пакет не обещает исправить произвольные побочные эффекты чужой функции.

Ожидаемые ошибки JSON, схемы и игрового API возвращаются как `nil, err` с использованием `goerrors 0.1.0`. Неверные типы аргументов публичных функций и некорректные регистрации вызывают обычную строковую ошибку Lua. Сам пакет не печатает сообщения и не создаёт логгер. Неизвестные структурные поля, имена и недоступные для записи свойства отклоняются.

## Подробности проверок

Unit-тесты Busted под Lua 5.2 находятся рядом с модулями. Разбор проверяется через реальный JSON-декодер; игровые объекты заменяются проверочными функциями создания. Проверяются структура и ошибки JSON, выбор схем, родители и порядок детей, идентичность найденных объектов, независимость экземпляров, специальные значения, порядок присваиваний и очистка при отказе. Отдельно проверяются повторное удаление, ручной перенос и сохранность чужих ресурсов и соседей.

Для `manual_test` предлагаются команды `ui_schema_test open <case>`, `step <action>`, `report`, `close` и `stop` с тем же префиксом. `open` выбирает меню, `step` выполняет заранее описанное действие, `report` сообщает результат, `close` удаляет меню, `stop` также снимает тестовые команды и временные обработчики. Запуск и остановка не должны накапливать их после повторного подключения.

После действия запуск ожидает минимум два завершённых кадра обновления/отрисовки, затем выдаёт `ready`, если проверки выполнены. Ожидание ограничено таймаутом и не останавливает игру; подходящее игровое событие проверяется при реализации. Отчёт содержит номер запуска, сценарий, шаг, ожидаемые и фактические значения, версии игры и платформы, размер окна, масштаб UI и положение проверяемых компонентов.

Снимок должен соответствовать номеру запуска и шагу отчёта. Для его получения достаточно внешнего инструмента управления компьютером; игровую функцию сохранения скриншота создавать не обязательно. Отчёт доступен через консоль; запись в разрешённый каталог игры желательна, если это позволяет установленный LuaCs. Сервер управления по сети не требуется.

Основные меню проверяются при обычном и уменьшенном размере окна; размеры фиксируются в отчёте. Командный вызов обработчика дополняется настоящими кликами и вводом. Для каждого встроенного описания типа нужна проверка создания и очистки в клиенте; необходимые ресурсы для особых типов указываются явно. Невыполненные проверки перечисляются, а прохождение unit-тестов не объявляется визуальной проверкой игры.

## Среда и проверенные источники

Пакет рассчитан на Lua 5.2 через LuaCs/MoonSharp и создание UI на клиенте. Разбор и проверка данных не должны требовать запущенного GUI; попытка построения на выделенном сервере возвращает ошибку до создания объектов. Подключение пакета само по себе не создаёт окна и не устанавливает постоянные обработчики обновления и рисования. Подключение конкретного меню к игровому циклу остаётся в вызывающем коде.

По проектным соглашениям нужны отдельные `.d.lua`, README на русском, фиксированные версии зависимостей, форматирование и линт изменённого Lua. Ожидаемые ошибки использует `limanchel.pkg.goerrors.v0_1_0.goerrors`. JSON-декодер — внутренняя зависимость, которую выберет разработчик. Собственный C#-мост не планируется.

До реализации нужно составить список доступных средств построения UI целевой версии: способы создания, области детей, требования к ресурсам и очистка. Проверяются также необычные объекты вроде контекстных меню, графиков и воспроизведения медиа: они не обязаны работать как обычная панель. Служебные фасады, перечисления и абстрактные классы не становятся создаваемыми компонентами только из-за присутствия их имён в экспорте.
